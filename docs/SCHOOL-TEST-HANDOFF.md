## 손글씨 테스트 원고

아래 글은 기능 시험용입니다. A와 B는 같은 바탕에서 오류 하나의 영향을 비교하도록 만들었습니다. 좋은 글에 억지로 고칠 점을 만들 필요는 없습니다.

### A. 이유 누락 + 분명한 맞춤법 오류

> 함께 달걀을 지킨 아이들
>
> 『호랑이를 부탁해』는 아이들이 달걀 부화 실험을 하며 겪는 일을 그린 동화입니다.
> 아이들은 깨진 달걀을 발견하고 범인을 의심합니다. 하지만 남은 달걀을 함께 지키기로 하고 병아리들을 부화시킵니다.
> 저는 아이들이 검은 모자와 대화하는 장면이 가장 인상적이었습니다.
> 이 책은 서로를 이해하고 용서하는 모습을 보여 주는 점이 좋습니다. 친구와 다툰 친구들에게 추천하고 십습니다. 사과를 받아들이는 마음을 생각해 볼 수 있기 때문입니다.

기대할 점:

- “십습니다” → “싶습니다”를 표기 오류로 안내합니다. 단, OCR가 실제 쓴 글을 잘못 읽었다면 먼저 인식 문제로 다뤄야 합니다.
- 인상적인 장면은 있지만 **그 장면이 인상적인 까닭**이 없다는 점을 짚고, 학생이 까닭을 쓰도록 질문합니다. 뒷부분 평가의 까닭과 구분되는지도 살펴봅니다.
- 학생 대신 문단을 완성해서 주지 않습니다. 빠진 요소는 첫 화면에 모두 표시하고, 자세한 내용 카드만 최대 1개, 확실한 표기 오류는 개수 제한 없이 모두 표시합니다.
- 제목의 매력이나 평가의 설득력 때문에 단정적인 감점을 하지 않습니다.

### B. A를 고친 비교 원고

A의 인상적인 장면 문장 다음에 아래 문장을 추가하고, “십습니다”를 “싶습니다”로 바꿉니다.

> 서로를 의심하던 아이들이 대화를 통해 오해를 풀어 가는 모습이 마음에 남았기 때문입니다.

기대할 점:

- A에서 지적한 두 문제가 사라졌다면 같은 지적을 반복하지 않습니다.
- 명확히 고칠 부분이 없다면 카드가 없어도 정상입니다. 다만 교사 확인이 필요하다는 안내나 기준별 상태가 이해되는지 확인합니다.
- 잘 썼다는 사실만으로 “완벽한 글”이라고 단정하지 않습니다.

### C. 교사에게 넘길 판단 (여유가 있을 때)

B의 인상적인 까닭만 “재미있었기 때문입니다.”로 바꿉니다.

- 까닭은 존재하므로 **까닭이 없다**고 단정하면 안 됩니다.
- 구체성·설득력 판단은 교사가 맡습니다. AI가 다룬다면 교사 확인 사항으로 구분해야 합니다.

### D. 촬영 문제와 글씨 문제 (여유가 있을 때)

- 같은 원고를 흐리게 찍거나 일부를 잘라 올려봅니다. 다시 촬영하도록 안내하고, 학생 글씨 탓으로 돌리지 않는지 봅니다.
- 사진은 선명하지만 글씨를 알아보기 어려운 경우에는 또박또박 쓰도록 정중히 안내하는지 봅니다. “예쁘게 써라”처럼 모양을 평가하거나 학생을 탓하지 않습니다.
- 애매한 글자를 추측해 맞춤법 오류로 확정하면 안 됩니다. 구별할 수 없으면 교사 확인으로 넘깁니다.

## 화면과 수업 흐름 체크

- [ ] 왼쪽 사진 / 오른쪽 카드가 읽기 편하다. 작은 화면에서도 사용할 수 있다.
- [ ] 카드 번호를 누르면 해당 사진의 해당 줄을 찾을 수 있다. 확대해도 위치가 맞는다.
- [ ] 2쪽 이상 올릴 때 올바른 쪽과 줄을 가리킨다.
- [ ] 종이에 직접 고친 뒤 수정 표시와 교사 확인 요청을 할 수 있다.
- [ ] 교사는 같은 사진·카드·요청 상태를 볼 수 있다.
- [ ] 교사 메모를 남기면 학생 화면에서 확인할 수 있다.
- [ ] “잘못 읽었어요” 등 도움 요청을 교사가 확인할 수 있다.
- [ ] 교사가 접수를 닫으면 새 제출이 막힌다. 시험 뒤 필요한 상태로 돌려놓는다.
- [ ] 공용 기기는 학생이 바뀔 때 ‘사용 마치기’를 사용한다.

사진 업로드는 1회 최대 4쪽입니다. 현재 제출 제한은 번호당 하루 4회, 학급 하루 120회이며 실패한 외부 분석 요청도 횟수에 포함될 수 있습니다. 25번의 집 테스트가 제한에 영향을 줄 수 있으므로 무작정 반복하지 말고 남은 시험을 나눠 진행하세요. 제한은 Cloud 결제의 지출 상한이 아닙니다.

## 다음 수정 요청 — 아직 구현하지 않음

**실제 학급은 1~23번이며 4번이 없습니다. 총 22명입니다.** 선생님이 “나중에 수정”을 요청했으므로 현재는 테스트를 위해 기존 1~40번 접속을 유지했습니다.

학교 테스트 후 수정할 때:

- 학생 선택 목록과 서버 검증을 모두 `1, 2, 3, 5, …, 23`으로 맞춥니다. 화면에서만 숨기지 않습니다.
- 관련 파일: `app/reviewer.tsx`, `app/api/student/route.ts`. 안내 문구와 README, 필요한 검증도 함께 갱신합니다.
- 기존 25번 테스트 자료를 실제 학생 자료로 옮기지 않습니다. 필요 없어진 시험 자료는 교사가 확인 후 삭제합니다.
- 학생 공개 전 교사 소유권과 학교 기기 접속을 확인하고, 선생님이 공개를 요청하면 현재 사이트의 접근 설정을 변경합니다. 새 사이트를 만들지 않습니다.

## 학교 Codex에게: 유지할 교육 기준

종이에 초고 작성 → 사진 → AI의 첫 고쳐쓰기 → 종이에 수정 → 교사가 두 번째 피드백. 학생과 생성형 AI의 자유 대화, 글 대필, 점수 매기기는 넣지 않습니다.

| 요소 | AI가 확인할 범위 | 교사가 볼 부분 |
| --- | --- | --- |
| 제목 | 제목 유무 | 관심을 끄는지, 핵심을 담는지 |
| 책 소개 | 책 제목과 소개 내용 유무 | 소개가 정확하고 적절한지 |
| 줄거리 | 줄거리 유무, 명백하게 흐름이 끊긴 부분 | 실제 책과 일치하는지, 핵심 사건 선정·분량 |
| 인상적인 부분과 까닭 | 특정 장면·표현 및 까닭 유무 | 까닭의 관련성·구체성·깊이 |
| 책 평가 | 좋거나 아쉬운 점과 까닭 유무. 추천했다면 대상과 까닭 확인 | 평가의 설득력과 타당성 |
| 맞춤법 등 | 확실히 읽힌 글자의 맞춤법·띄어쓰기·문장부호 | 판독이 어렵거나 문맥 판단이 애매한 경우 |

작가·출판사 등 책 소개 예시를 전부 필수로 만들지 않습니다. 추천 자체, 개인 경험, 인용, 장단점 둘 다 쓰기, 고정 글자 수나 문단 순서는 필수가 아닙니다. “요소 존재”와 “잘 드러나는가”를 구분하고 후자의 모호한 판단은 교사에게 넘깁니다.

## 학교 Codex에게: 작업 위치와 연결 상태

- 먼저 저장소를 clone/pull하고 이 문서와 `README.md`, `docs/TEACHER-GUIDE.md`, 적용되는 `AGENTS.md`를 읽습니다. 로컬 경로는 학교 컴퓨터에 맞게 선택합니다.
- Windows PowerShell에서 한글이 `?쒗룊`처럼 보이면 파일을 고치기 전에 `Get-Content -Encoding UTF8 docs/TEACHER-GUIDE.md`처럼 UTF-8로 읽습니다. 이번 집 환경에서는 기본 인코딩으로 읽을 때만 깨져 보였고 UTF-8 원본은 정상이었습니다. 깨져 보이는 터미널 출력을 파일에 덮어쓰지 않습니다.
- 기존 Sites 프로젝트는 `.openai/hosting.json`의 값을 사용합니다. 같은 사이트를 재생성하지 않습니다. Sites 도구가 없다면 GitHub 작업까지 진행하고 배포 미완료임을 알립니다.
- 서버 설정: `GOOGLE_SERVICE_ACCOUNT_JSON`은 secret, `GOOGLE_CLOUD_PROJECT=book-review-reviewer`는 일반 환경값입니다. 이미 Sites에 등록되어 있으므로 학교에서 배포된 앱을 시험하는 데 키를 다시 옮길 필요가 없습니다.
- 집의 키 파일과 `.env`, `work/`, 학생 사진, DB는 Git에 넣지 않습니다. 키 내용이나 토큰을 채팅·로그에 출력하지 않습니다. 로컬 실제 분석이 필요할 때만 별도로 안전하게 자격증명을 구성합니다.
- 소스: `lib/google.ts`(Vision/Vertex 호출과 프롬프트), `lib/validation.ts`(원문 일치·신뢰도·카드 제한), `lib/review.ts`(스키마·기준), `app/reviewer.tsx`(학생 화면), `app/teacher/teacher-dashboard.tsx`(교사 화면), `lib/server.ts`(권한/저장).
- 저장소 푸시는 소스 동기화입니다. 서버 비밀 설정 및 사진·DB가 GitHub로 복제되는 것은 아닙니다. 기능 수정 후에는 별도 Sites 배포가 필요합니다.
- 기존 검증: TypeScript, 피드백 검증 테스트 7개, 자격증명 없는 로컬 API 검사, 프로덕션 빌드 통과. 이번 인수인계 작성은 문서 변경만입니다.

필요한 코드 변경 후 검증:

```sh
node node_modules/typescript/bin/tsc --noEmit
node --test tests/feedback.test.ts
npm run build
```

Windows에서 npm 실행 문제가 나면 README의 실제 npm 진입점 명령을 참고합니다. `scripts/api-check.mjs`는 자격증명이 없는 로컬 시험 환경 전용이며 연결된 운영 서버에서 실행하지 않습니다. 운영 DB 마이그레이션을 다시 만들거나 기존 기록을 초기화하지 않습니다.
